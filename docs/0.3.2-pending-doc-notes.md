# 0.3.2 docs still to update after the in-review branches merge

The `docs/release-0.3.2` branch documents `release/0.3.2-candidate` at
`23dda21` only. When each branch below merges, update the places listed for
it, then delete this file before the release.

Two files describe the candidate's exact in-app messages and will need the
most care:

- `SETUP.md`, **If something goes wrong**: three tables (iPad, PC, Windows).
  Each row is the message word for word, what it means, and what to do.
- `scripts/QUICKSTART.txt`, **If something goes wrong**: a short version of
  the same messages. It ships in the installer and the Start menu.

`docs/known-issues.html` (published as
https://eternalmonitor.dev/known-issues.html) lists problems the candidate
still has. Remove or reword an entry once a merged branch fixes it, and add a
line to `RELEASE_NOTES.md` instead.

`scripts/check_messages.py` checks every message quoted in those two files
against the string literals in `host/src` and `ios/EternalMonitor`, and
`scripts/test_check_messages.py` runs it in CI. A branch that rewords a
quoted message fails that test until the quote is updated, which is the
point. Placeholders such as `{version}` are written as `…`.

## Release prep (not a builder)

- Version mentions to bump when 0.3.2 is published: `README.md` (Download
  table and Status), `SETUP.md` (Steps 1 and 2), `docs/index.html` (hero
  eyebrow, Status card, timeline, FAQ), `docs/download.html` (hero, cards,
  meta description, `data-release`), `docs/latest.json`. `scripts/check-versions.sh`
  checks only `latest.json` against `download.html`.
- `scripts/QUICKSTART.txt` and `SECURITY.md` no longer name a version, so they
  need no bump.
- Known issues is a website page, `docs/known-issues.html`. The website links
  to it site-relative. README, SETUP and QUICKSTART link to
  https://eternalmonitor.dev/known-issues.html. GitHub Pages builds the site
  from `main` `/docs`.
- Release gate: before building the installer, `.github/workflows/release.yml`
  runs `scripts/check_published_site.py`. It needs
  https://eternalmonitor.dev/known-issues.html and
  https://eternalmonitor.dev/latest.json to answer 200, retrying with
  growing waits for about ten minutes while a Pages deploy finishes. It also needs `latest.json`'s
  Windows version to be no newer than the tag. A final tag (`vX.Y.Z`, no `-`)
  fails the release otherwise. A pre-release tag or a dry run only warns. So:
  merge the release to `main`, wait for the Pages deploy, then push the tag.
  If the gate still fails because Pages took longer, nothing was built or
  published: rerun the failed workflow (Actions, **Re-run jobs**) once the
  Pages deploy has finished. There is no need to delete or move the tag.
- `latest.json` can't name the tag's own version at that point. It carries
  the SHA-256 of the installer this workflow builds, and the site PR updates it
  after Apple approves the matching iPad build (for 0.3.1: tag `d256668`, then
  `0118e53`). The gate only rejects a version newer than the tag.
- `docs/latest.json` is not on `main` yet, so https://eternalmonitor.dev/latest.json
  returns 404 today, as does known-issues.html. A final 0.3.2 tag pushed before
  the release merge reaches `main` would fail the gate.
