# Host settings

The host offers 30, 60, 90 and 120 fps. An iPad requesting 30, 60 or 120 fps caps the host at the lower of the two settings. Disconnecting clears the client cap without changing the host preference. The iPad's Frame Rate setting applies on the next connection.

Encoder input defaults to YUV420. BGRA and Auto are opt-in until both NVENC and AMF pass the reference PC's color comparisons and ten-minute stability runs. Auto chooses BGRA, then BGR0, only when the encoder advertises support. It otherwise chooses an advertised 8-bit 4:2:0 format, preferring YUV420P and using NV12 for Intel Quick Sync. The default YUV420 setting follows the same format selection. libx264 always uses YUV420P. BGRA avoids the host's color conversion step. An unsupported forced BGRA setting reports an encoder error. Changing this setting requires a stream restart; the Settings page offers Restart now. `ETERNAL_INPUT=auto`, `bgra` or `yuv420` overrides the saved setting at launch.

At stream startup the host tries the selected hardware encoder, then the other Windows hardware backends if it cannot open. It uses libx264 only after those attempts fail. Selecting libx264 explicitly keeps CPU encoding. The session log records each failed encoder and the one that opened.

The Connected iPad card shows the latest receiver report. Unrecovered loss counts fragments still missing after repair. Repaired fragments have their own percentage. Both percentages use received, repaired and still-missing fragments as the total. A zero latency estimate displays Measuring until a measurement is available.

The update check runs on a background thread. It reads `https://eternalmonitor.dev/latest.json` at startup when the last check is over an hour old, then once a day, counting failed checks. Check now in Settings checks at once. Turn off Check for updates automatically to stop automatic checks; the banner then stays hidden unless you check by hand. Requests carry no identifiers. A newer version shows a banner above every page and one Windows notification per version. Later hides the banner for that version for a day, across restarts.

Update now downloads EternalMonitor-Setup.exe into a new, randomly named folder under `%LOCALAPPDATA%\EternalMonitor\updates`. The installer URL must be the GitHub release asset for that version. Every redirect must stay on github.com, objects.githubusercontent.com or release-assets.githubusercontent.com over HTTPS. Its size must equal the release asset's, and its SHA-256 must equal both `latest.json` and the hash in the GitHub release body. Any failure deletes the download and offers Try again and Download from the website. While an iPad is connected, the update waits until streaming has been off for three seconds, unless the user chooses Stop and update. Stop and update ends the stream when the update takes over and tells the iPad, which shows "Your PC ended the session." The host then refuses new iPad connections (they see Busy) and, if an iPad connected first, goes back to waiting for the stream to stop. It checks that the update folder and every folder above it are real folders, not links, copies EternalMonitor-updater.exe there, starts it suspended and lets it run only if Windows started that exact copy. The helper loads DLLs only from System32 (static C runtime, `/DEPENDENTLOADFLAG:0x800` and `SetDefaultDllDirectories`). It pins the update folder, opens the installer so no other process can write, rename or delete it, checks the SHA-256 from that open handle, opens the host process and reports ready. Only then does the host close normally; if the helper exits, reports an error or stays silent for 30 seconds, the host stays open and shows the failure with Download from the website. The helper waits up to 60 seconds for that host process to exit; if it is still running, it does not run Setup. Otherwise it starts Setup suspended with `/SP- /SILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS /NORESTARTAPPLICATIONS`, resumes it only if Windows mapped the very file it verified (volume and file ID, not the path), and holds the installer until Setup exits. See SECURITY.md for the threat model. It then starts the installed host again, even if Setup failed, the user declined the Windows prompt or the old host took longer than 60 seconds to close. It always waits for the old host process to exit first, without a deadline: a start while the old host runs would only show its window and quit, leaving nothing running once the old host closed. The relaunched host reports whether the version changed. Debug builds read `ETERNAL_UPDATE_BASE` (for example `http://127.0.0.1:8765`) instead of the real site, for end-to-end tests.

Only one host runs per installation and settings folder, compared by their final paths, so a short name or a junction to the same install counts as the same. A second launch brings the running window forward and exits before it touches the virtual display, so an update can never close another host's stream.

When an iPad's HELLO2 protocol range excludes the host's, or a v0.1.x app connects, the host names the side that must update. An older PC gets Update now; an older iPad gets TestFlight instructions.

Each host launch and each 2 MiB of output rotates `eternal-host-session.log` into `.1`, retaining `.2` as well. Copy logs includes these files, startup evidence and the most recent memory log so queued errors are included. Reports expose queue drops and storage failures. Saved support logs and exports redact pairing codes and tokens; the headless console still prints the pairing code for local automation. Startup reports include Windows build, CPU/RAM, all DXGI adapters and driver versions, FFmpeg library versions and compiled encoder availability. Encoder attempts include advertised pixel formats and numeric FFmpeg errors; native FFmpeg warnings and errors enter the same support log. A ten-second summary records session ID, actual codec, capture/encode/send counters, USB state, heartbeat ages and effective frame/packet settings. The Windows headless host handles Ctrl+C and Ctrl+Break through the normal shutdown path.

The installer registers UDP and TCP firewall rules for its installed host executable on domain, private and public networks. Uninstall removes those rules. It also grants local users read and execute access to its display tasks. A failed task produces the reinstall guidance and records Windows' exact error in the host log. A task that runs but times out waiting for a display instead asks the user to check the display and driver.

Local format selection, frame-rate negotiation, release version comparison and log rotation tests pass. Hardware BGRA, task permissions, installer lifecycle and native GUI evidence remain required before the P6 gate can pass. YUV420 remains the default while those checks are pending.
